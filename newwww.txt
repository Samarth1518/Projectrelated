# 1. PROJECT OVERVIEW

The Satellite Testing Dashboard is a Python-based application designed to process satellite testing reports in PDF format, extract procedure execution information, organise the extracted information into JSON, compare the procedures against their respective subsystems, and display the results through an interactive web dashboard.

The main purpose is to make satellite testing results easier to analyse and understand.

Instead of manually checking large PDF reports and calculating subsystem-wise Success and Failure counts, the application automates the process.

### Main objectives

1. Upload multiple satellite testing PDF reports.
2. Extract procedure names and execution information.
3. Identify STEP IDs and their execution statuses.
4. Convert the extracted information into a structured JSON file.
5. Identify unique procedures and their execution histories.
6. Match procedures against subsystem configurations.
7. Determine the latest execution status.
8. Calculate subsystem-wise Success and Failure counts.
9. Display the results through an interactive dashboard.
10. Show unmatched, ambiguous and unassigned procedures separately.

The application is deterministic and rule-based. It does not depend on AI models or external AI APIs.

This is the main functionality already implemented and tested.

### 4.1 Reading PDF files

The application reads all PDF files placed directly inside the `input/` folder.

The PDF text extraction function reads pages one at a time.

The relevant implementation uses:

```python
for page_number in range(page_count):
    page = get_page(document, page_number)
    page_text_parts.append(get_page_text(page) or "")
    page_text_parts.append("\n")
```

This allows the application to extract text page by page while retaining the text sequence needed by the parser.

The page boundary is preserved so that information continuing across pages can still be processed.

### 4.2 Extracting procedure metadata

The PDF reports contain information similar to:

```text
Procedure : abbnm
Time: 31-dec-2025 11:44:13.103
Mode: Manual
Source: abbvdskh
Dur: 203.96(s)
Priority: Low
```

The parser extracts relevant information, including:

- Procedure name.
- Execution date and time.
- Duration.
- STEP ID.
- STEP description.
- STEP status.
- Final execution status.
- Failure reasons.
- Operating mode information.

Other metadata is not necessarily included in the final dashboard calculations.

### 4.3 STEP ID extraction

The parser identifies STEP IDs using a regular expression.

```python
STEP_ID_RE = re.compile(r"^\s*(\d{2}\.\d{3,4})\b")
```

Example:

```text
01.0001
01.0002
01.0003
```

### 4.4 Execution statuses

Four STEP status categories are maintained:

```python
STATUS_NAMES = (
    "success",
    "failure",
    "suspend",
    "progress"
)
```

These statuses are stored separately in the JSON.

### 4.5 Final execution status

The existing simplified final-status logic is:

```python
if status["failure"]:
    final_status = "Failure"
else:
    final_status = "Success"
```

Therefore:
- If at least one STEP has failed, the execution is classified as Failure.
- If no failed STEP is detected, the execution is classified as Success.

**Important:** Suspend and Progress STEP statuses do not independently cause the final execution to be classified as Failure. This is the existing behaviour and should be verified against the actual reporting requirements before changing it.

| Metric | Count |

| Unique procedures present | 2 |

This counts unique procedure keys rather than execution records.

```python
def remove_old_generated_outputs():
    pattern = os.path.join(OUTPUT_DIR, "output_*.json")

    for path in glob.glob(pattern):
```

The user explicitly decided:

# 8. SUBSYSTEM MATCHING MECHANISM

This is one of the important parts of the dashboard.

The application compares procedure filenames configured in `subsystems.json` with the procedure names extracted from the PDF reports.

The matching logic uses Python's built-in `difflib` module.

No additional installation is required.

### 8.1 Filename normalisation

The existing matching code uses logic similar to:

```python
def normalize_name(name):
    name = os.path.basename(str(name)).strip().lower()
    name = re.sub(r"\s+", "", name)
    return name
```

This:
- Removes directory paths.
- Converts the name to lowercase.
- Removes whitespace.

Example:

| Original | Normalised |
|---|---|
| Voltage_Test | voltage_test |
| VOLTAGE_TEST | voltage_test |
| Voltage Test | voltagetest |

### 8.2 Exact matching

The application first checks for an exact match after normalisation.

```python
exact_matches = [
    name for name in json_names
    if normalize_name(name) == target
]
```

If a match is found, it is used without needing similarity matching.

### 8.3 Similarity matching

If exact matching fails, the program calculates similarity using:

```python
def similarity_score(name1, name2):
    first = normalize_name(name1)
    second = normalize_name(name2)

    return difflib.SequenceMatcher(
        None, first, second
    ).ratio()
```

The similarity result is between 0 and 1.

For example:
- 1.00 = 100%
- 0.95 = 95%
- 0.90 = 90%
- 0.89 = 89%

### 8.4 Similarity threshold

The configured threshold is:

```python
SIMILARITY_THRESHOLD = 0.90
```

The acceptance condition is:

```python
if score >= SIMILARITY_THRESHOLD:
    scored_matches.append((name, score))
```

Therefore, a match must have at least 90% similarity to qualify.

### 8.5 Selecting the best match

Candidates are sorted by their similarity score:

```python
scored_matches.sort(
    key=lambda item: item[1],
    reverse=True
)
```

The highest-scoring candidate is preferred.

If multiple candidates share the same highest score, the system treats the match as ambiguous rather than guessing.

### 8.6 Duplicate procedure names across subsystems

The user confirmed that the existing duplicate-handling behaviour should remain unchanged.

The current implementation uses:

```python
assigned_names = set()
```

If the same JSON procedure is already assigned to another subsystem, a later occurrence can be marked ambiguous.

The first subsystem processed gets priority.

Example:

```json
{
    "Power_Subsystem": [
        "Voltage_Test"
    ],
    "Communication_Subsystem": [
        "Voltage_Test"
    ]
}
```

If the procedure is assigned to Power Subsystem first, its later occurrence under Communication Subsystem is treated as ambiguous.

**Final decision:** Keep this behaviour. Do not allow duplicate assignments automatically or count the same procedure in both subsystems unless the user explicitly revisits this decision.

### 8.7 Unmatched and ambiguous procedures

- **Unmatched:** No reliable configured procedure match was found.
- **Ambiguous:** Multiple candidates or a duplicate assignment prevent a confident match.
- **Unassigned:** A procedure extracted from the PDF is not assigned to a configured subsystem.

These should be shown separately rather than being counted as Failure.

# 11. NEW MAJOR FEATURE: AUTOMATIC SUBSYSTEM CONFIGURATION PARSING

This is the next major feature to implement.

Currently, `subsystems.json` is manually maintained.

The user wants the application to extract subsystem names and procedure filenames automatically from an uploaded Word or PDF document.

The generated JSON will then be used by the existing dashboard matching logic.

### 11.1 New input workflow

The updated upload page should contain:

1. Project Name.
2. Test Report Files.
3. Subsystem Configuration File.
4. Date Selection.
5. Generate Dashboard button.

The test reports and subsystem configuration are separate uploads.

### 11.2 Supported subsystem document formats

The agreed formats to target are:

- `.docx` Word documents.
- Text-based `.pdf` documents.

The older `.doc` format has not been confirmed as directly supported.

### 11.3 Example subsystem document structure

The document may look like:

```text
PROJECT NAME

Subsystem: EXAMPLE

SI No | Function | Filename | Time | ... | Remarks

1     | Testing  | example.tst
2     | Testing  | file.tst
3     | Testing  | sample.tst
4     | Testing  | (*) SEM
```

The actual table may have approximately 19 or more columns.

Only the following information is relevant:

- The main `Subsystem:` heading.
- The `Filename` column.

All other table columns should be ignored.

### 11.4 Finding the Filename column

The parser must identify the column by its header name.

It must not assume that Filename is always in the third column.

For example:
- In one document, Filename might be the third column.
- In another, it might be the fifth column.

The parser should find the header named Filename and extract the cells belonging to that column.

### 11.5 Subsystem identification

Example:

```text
Subsystem: EXAMPLE
```

The parser should capture:

```text
EXAMPLE
```

The subsystem name should come from the main heading, not from other table columns.

If multiple subsystem headings are present, each should be represented separately.

If the same subsystem heading occurs more than once, its filename entries should be combined.

### 11.6 Filename extraction requirements

The Filename column may contain different formats.

The parser must handle these examples:

**Normal filenames**

```text
example.tst
file.tst
sample.tst
```

Expected:

```text
example.tst
file.tst
sample.tst
```

**Comma-separated values**

```text
example.tst, file.tst, sample.tst
```

Expected:

```text
example.tst
file.tst
sample.tst
```

**Split filename without extension**

```text
Hello-
Xn1,
Hello-
Xn3
```

Expected:

```text
Hello-Xn1
Hello-Xn3
```

**Split file extension**

```text
exe-
hekllo.t
st

super.t
st
```

Expected:

```text
exe-hekllo.tst
super.tst
```

**Split prefix and extension**

```text
SO1-
on.tst

SO2-
on.tst
```

Expected:

```text
SO1-on.tst
SO2-on.tst
```

### 11.7 Additional filename rules

The parser should:
- Preserve original spelling and capitalization.
- Support `.tst` and `.sh`.
- Support filenames without extensions when appropriate.
- Handle comma-separated entries.
- Handle entries on separate lines.
- Reconstruct filenames split across lines or cell fragments.
- Ignore non-filename text such as `(*) SEM`.
- Ignore unrelated remarks and descriptions.
- Avoid joining unrelated filenames just because they are on consecutive lines.
- Remove duplicate filenames within the same subsystem.

The parser must use the actual document layout and table structure wherever possible. It should not simply join every consecutive line.

# 12. HOW subsystems.json SHOULD BE REPLACED

The user initially requested that each new subsystem document should replace all previous subsystem data.

This means:
- A new upload should not merge with the previous configuration.
- Old subsystem names and filenames should disappear after a successful replacement.
- The new document should become the source of the current subsystem configuration.

However, an important safety rule was subsequently agreed:

**Preserve the previous valid `subsystems.json` if a newly uploaded document fails to parse or validate.**

The agreed replacement process is:

```text
Upload Subsystem Document
          |
          v
   Parse Document
          |
          v
 Extract Subsystems
          |
          v
 Extract Filenames
          |
          v
    Validate Data
          |
          v
 Create Temporary JSON
          |
          v
 Validate Generated JSON
          |
          v
 Replace subsystems.json
```

Validation should check:
- At least one valid subsystem exists.
- Subsystem names are not empty.
- Each subsystem has a valid filename list.
- Procedure names are not empty.
- Duplicate filenames within a subsystem are removed.
- The resulting JSON has the expected structure.

If parsing fails, the existing valid `subsystems.json` must remain untouched.

This gives the desired behaviour: a successful new upload completely replaces the old configuration, while a failed upload does not destroy working data.

# 13. NEW FEATURE: DATE FILTERING

The dashboard upload page will include a date selection option.

There will be two ways to generate the dashboard:

1. Overall.
2. Custom date range.

### 13.1 Overall option

Overall should be a selectable option.

When selected:
- All available execution records are considered.
- The dashboard behaves like the current implementation.
- The latest execution of each procedure is selected from the complete dataset.
- The date displayed at the top-right is the oldest to latest valid execution date in the generated JSON.

Overall should be the default selection.

### 13.2 Custom date range

The upload page will include:
- Start Date.
- End Date.

The user can choose both dates.

The dashboard will use only executions whose dates fall within the selected range.

Both boundaries are inclusive.

### 13.3 Same-day date selection

The system must support:

```text
Start Date: 01-11-2024
End Date:   01-11-2024
```

This should include every execution that occurred on 1 November 2024.

### 13.4 Example

Suppose the execution JSON contains:

| Procedure | Execution date | Status |
|---|---|---|
| Example.tst | 01-11-2024 | Success |
| Example.tst | 02-11-2024 | Failure |
| Sample.tst | 03-11-2024 | Success |
| Sample.tst | 05-11-2024 | Failure |

**Scenario A: Overall**

All executions are considered.

Latest execution:
- Example.tst → Failure.
- Sample.tst → Failure.

**Scenario B: 01-11-2024 to 03-11-2024**

Only executions in that date range are considered.

Latest execution within that range:
- Example.tst → Failure.
- Sample.tst → Success.

**Scenario C: 01-11-2024 to 01-11-2024**

Only executions on that date are considered.

- Example.tst → Success.
- Sample.tst → No execution in this range.

### 13.5 No execution in the selected range

A configured procedure may not have any execution during the selected period.

It must not be automatically classified as Failure.

The proposed display is:

`No execution in this range`

This is a separate condition and should not be counted as Success or Failure.

The final presentation of this condition should be confirmed during implementation if necessary.

### 13.6 Date range displayed on the dashboard

For Overall:

```text
Date: Oldest execution date – Latest execution date
```

For a custom range:

```text
Date: Selected Start Date – Selected End Date
```

### 13.7 Date filtering must not affect subsystem configuration

The date filter applies only to the execution JSON generated from the uploaded PDF reports.

It does not apply to the subsystem configuration document.

The subsystem document provides the procedure-to-subsystem mapping, independent of execution dates.

The original execution JSON should not be permanently modified by filtering.
